A plain-language guide to the whole project

W-SENTRY, explained from the ground up

An intrusion-detection system for wireless and IoT networks, and a study of a problem the field usually ignores: a detector that scores 99% on its own test data can collapse to near-zero on traffic from a different network. This guide explains what we built, why, how it works, and every technical term in it — so that after reading it, nothing about the project is a mystery.

Team: M. Vikas Goud · Riteesh Thiruveedhula · Shaik Gafar · V. Sai Tarun Reddy Guide: Mr. Bapu Sreenivas

01 What W-SENTRY is

W-SENTRY is an intrusion detection system (IDS) for wireless and Internet-of-Things networks, plus a research study measuring how well such detectors survive being moved to a network they were not trained on.

An intrusion detection system watches network traffic and flags malicious activity. W-SENTRY classifies each piece of traffic into one of five categories: Normal, Jamming, Spoofing, DoS/Flooding, and Intrusion/Probe. It does this with machine-learning models trained on three public attack datasets.

The project has three parts:

  • The models — classical machine learning (Random Forest, XGBoost) and a custom deep-learning model (a hybrid CNN-BiLSTM-Attention network), plus a domain-adaptation variant (DANN).
  • The study — a careful measurement of the "domain gap": how much accuracy is lost when a model trained on one network's data is tested on another's.
  • The dashboard — an obsidian-themed Security Operations Center (SOC) interface that visualizes all the results and runs a simulated live threat monitor.
The one-sentence version We built a wireless IDS, discovered that detectors fail badly across different networks, and showed that the right features and a domain-adaptation technique can close most of that gap.

02 The problem we are solving

A security model that looks excellent in the lab can be nearly useless in the field, and the usual way of reporting results hides this completely.

Almost every published IDS is trained and tested on the same dataset. On that dataset it reports very high accuracy — often above 95%. The unspoken assumption is that this number tells you how the model will behave once deployed. It does not.

We measured the failure directly. A Random Forest trained on the WSN-DS dataset scored 99.6% on its own test data. When we fed it traffic from a different dataset, CIC-IoT-2023, its accuracy fell to 0.18% — worse than guessing.

The reason is the domain gap: different networks produce different kinds of data. One dataset describes sensor-network routing behaviour; another describes internet packet flows; a third describes industrial-protocol headers. A model that memorized the shape of one kind of traffic has learned almost nothing about the others.

This matters because real deployments are never identical to the training lab. A hospital's IoT network, a factory floor, and a smart-city sensor grid all look different. If an IDS only works on the exact data it was trained on, its headline accuracy is a mirage.

The question we ask How much accuracy does an IDS actually lose when the training and deployment environments use different wireless protocols — and can we build a model that survives the move?

03 What already existed, and where it fell short

Prior work produced strong single-dataset detectors and early deep-learning architectures, but almost none of it tested the one thing that matters for deployment: cross-dataset transfer.

We surveyed recent studies. They fall into a few groups:

Prior approachWhat they didThe gap they left
ML for IoT security (Zhukabayeva 2025)Random Forest / XGBoost on IoT trafficNo deep learning, no cross-dataset test
CNN + RNN for WSN (Sinha 2025)Deep models on several benchmarksTrained and tested on each separately
6G sensor security (Khan 2025)Transformers, VAE-LSTMLimited to 6G scenarios only
Jamming detection (Terraf 2026)Transfer learning for jammingSingle attack type only
CNN-LSTM-Attention (Phalaagae 2025)The architecture closest to oursNo cross-dataset, no domain adaptation

Two patterns stand out. First, the strong results are almost always single-dataset — the model never meets unfamiliar traffic. Second, where transfer learning appears, it is narrow (one attack type, one scenario). Nobody had systematically measured the degradation across several full wireless/IoT benchmarks and then tried to close it.

That is the specific gap W-SENTRY fills.

04 How we approached it

Instead of chasing a higher single-dataset number, we built the measurement first, then engineered features and models specifically to survive crossing between networks.

Step 1 — Speak one language across datasets

The three datasets name their columns differently and measure different things. We built a behavioral feature mapping that projects every dataset into the same 20 protocol-agnostic features — things any network has, like traffic volume, rate, burstiness, how often connections start and stop, and port diversity. This common vocabulary is what makes cross-dataset comparison meaningful at all.

Step 2 — Clean the data so extreme values don't dominate

Some fields have enormous ranges (one column averaged 1.7 billion). We apply a log-scale normalization that compresses these without destroying their order, then standardize everything. This one preprocessing choice turned out to matter more than any model change (see §7).

Step 3 — Build and compare models

  • Baselines: Random Forest and XGBoost — strong, fast, conventional.
  • Hybrid deep model: a CNN-BiLSTM-Attention network that reads short sequences of traffic and learns spatial patterns (CNN), time patterns (BiLSTM), and which moments matter most (attention).
  • DANN: a version trained to produce features that work across datasets, using a trick called a gradient reversal layer.

Step 4 — Measure transfer, honestly

We test every model on every dataset — its own and the others — and lay the results out in a 3×3 transfer matrix. The diagonal is the familiar "same-dataset" number; everything off the diagonal is the real-world test.

Step 5 — Make it legible

Finally, a React SOC dashboard turns all of this into an operator's view: performance charts, the transfer heatmaps, a simulated live packet monitor, and a mitigation log.

05 Our innovation — what is actually new here

The contribution is not a single model. It is a measurement nobody had made, a feature design that makes transfer possible, and two findings that change how these systems should be built and reported.

  1. A full 3×3 cross-dataset transfer matrix. We quantify exactly how much accuracy is lost moving between three real benchmarks — the number the field usually omits. For Random Forest, the average off-diagonal accuracy is just 18.2%, a domain gap of 78.8 points.
  2. A 20-feature behavioral mapping. By describing traffic in protocol-agnostic behavioural terms, heterogeneous datasets become comparable and a model trained on one can carry real signal to another.
  3. Deep learning recovers transfer — dramatically in one direction. The hybrid model lifts WSN→Edge transfer from 11.9% (Random Forest) to 80.7%. The deep model learns patterns that generalize where simple decision rules cannot.
  4. One DANN for two domains, no tuning. A single domain-adversarial model handles both CIC-IoT and Edge-IIoT at 96.3–96.5% with no per-dataset fine-tuning — robustness bought for about a one-point accuracy cost.
  5. Preprocessing beats architecture. Log-scale normalization lifted Edge-IIoTset accuracy from 56.8% to 94.4% — a bigger gain than any change to the model. This is a warning to the whole field: reported accuracy can hinge on a single unreported line of preprocessing.
The headline Cross-dataset transfer depends more on feature-layer compatibility and preprocessing than on model architecture. Where two networks share underlying behaviour, a deep model transfers at 80%+; where they don't, no architecture saves you.

06 How the project works, end to end

Data flows through five stages, from raw benchmark files to an operator watching a live threat feed.

STAGE 1
Datasets
WSN-DS, CIC-IoT-2023, Edge-IIoTset — raw labeled traffic.
STAGE 2
Features
Map to 20 behavioral features, log-normalize, scale, window into sequences of 5.
STAGE 3
Models
RF & XGBoost baselines; hybrid CNN-BiLSTM-Attention; DANN for transfer.
STAGE 4
Evaluation
Same-dataset accuracy, the 3×3 transfer matrix, calibration.
STAGE 5
SOC dashboard
Charts, heatmaps, a simulated live monitor and mitigation log.

Training (Phases 1 & 2)

Phase 1 trains the classical baselines and produces the Random-Forest transfer matrix. Phase 2 trains the hybrid deep model and the DANN, produces the behavioural transfer matrix, and calibrates confidence. Both phases write their numbers to JSON result files that everything else reads.

The live monitor (dashboard)

In a real deployment, a packet sniffer would capture traffic off a network card, the feature extractor would turn each short window of packets into the 20 features, the trained model would classify it, and a mitigation engine would issue a firewall rule for anything malicious. In the shipped dashboard, this entire live path is simulated in the browser so the demo runs with no backend — see §9.

Mitigation

When a threat is detected with high confidence, the mitigation engine decides a response by attack type — block the source IP, rate-limit it, or (for jamming, which can't be blocked at the network layer) raise an alert — and logs the firewall command it would run. A cooldown prevents the same address from being acted on repeatedly.

07 The metrics, and how to read them

Every number in the project is one of these. Here is what each one means in plain terms, and what "good" looks like.

Accuracy

The share of all predictions that were correct. Simple, but misleading when one class dominates: if 97% of traffic is Normal, a model that always says "Normal" scores 97% while catching zero attacks. That is why we also use the metrics below.

Precision & Recall

These are a pair, best understood for a single attack type:

  • Precision — of everything the model flagged as "Spoofing," how much really was. Low precision means false alarms.
  • Recall — of all the real Spoofing in the data, how much the model caught. Low recall means missed attacks.

There is usually a trade-off: flag more aggressively and you catch more (higher recall) but cry wolf more (lower precision).

F1 score

A single number that balances precision and recall (their harmonic mean). It is high only when both are high, so it is the fairest one-number summary for a class. Ranges 0–1 (or 0–100%).

False Alarm Rate (FAR)

Of all the genuinely benign traffic, how much was wrongly flagged as an attack. Lower is better. A high FAR exhausts human analysts, who stop trusting the alerts.

Confusion matrix

A grid with true classes down the side and predicted classes across the top. The diagonal is correct predictions; everything off it is a specific mistake (e.g., "real DoS called Normal"). It shows not just how often the model is wrong but how.

Transfer accuracy & the domain gap

Transfer accuracy is simply accuracy measured on a different dataset than the model trained on. The domain gap is the drop from same-dataset accuracy to cross-dataset accuracy. A small gap means the model generalizes; a large gap (ours was 78.8 points for Random Forest) means it memorized.

Calibration: confidence, temperature & ECE

A model doesn't just predict a class, it reports a confidence. A calibrated model is honest: of the predictions it makes with 90% confidence, about 90% should be correct.

  • ECE (Expected Calibration Error) measures that honesty gap. Lower is better; ours are all under 2%, meaning the models are already well-calibrated.
  • Temperature (T) is a single dial that corrects over- or under-confidence. T greater than 1 means the model was overconfident and its probabilities are softened.

ROC curve & AUC

As you make a detector more trigger-happy, it catches more real attacks (true-positive rate rises) but also raises more false alarms (false-positive rate rises). The ROC curve plots that trade-off; AUC (area under it) summarizes it in one number: 1.0 is perfect, 0.5 is a coin flip.

An honesty note on our ROC A true ROC curve needs the model's raw scores at many thresholds, which we haven't exported yet. The dashboard's ROC uses the single measured operating point from the confusion matrix, so its AUC is a lower-bound estimate, clearly labeled as such.

Transfer is not symmetric. WSN→Edge reaches 80.7%, but Edge→WSN stays at 27% — the sensor-network model generalizes outward, but the reverse direction doesn't map back cleanly. And CIC-IoT and WSN-DS barely transfer in either direction, because their features come from entirely different network layers.

Adding WSN-DS to the DANN broke it: routing-layer features share no structure with transport flows, so there is no common representation to find. This is the limit of domain adaptation — it bridges related domains, not unrelated ones.

The takeaway for anyone building an IDS Always report cross-dataset transfer alongside same-dataset accuracy. A 99% number from a single dataset tells you nothing about how the system behaves on traffic it has never seen.

09 What you need to know before it runs

A few facts prevent misreading the project — especially what is measured versus what is demonstrated.

Real vs. simulated — the most important distinction

  • Real: the datasets, the training, and every accuracy/transfer/calibration number. These come from actually running the models and are stored in phase1_results.json and phase2_results.json.
  • Simulated: the dashboard's Live Monitor and Mitigation engine. No packets are captured, no model runs in the browser, and no firewall rule is ever executed — a client-side generator produces a realistic-looking feed so the SOC workflow can be demonstrated without a backend. The netsh/iptables commands shown are illustrative.
  • Approximate: the dashboard's ROC curves (see §7).

What it takes to run

  • The ML pipeline needs Python with the project's requirements installed; run_phase1.py and run_phase2.py reproduce the results.
  • The dashboard needs Node.js; from frontend/, run npm install then npm run dev. It runs fully standalone on the simulated feed.
  • A true live demo (real packet capture) would additionally need administrator privileges and a capture driver (e.g. Npcap on Windows) — this is the part that is simulated in the shipped build.

Honest limitations

  • WSN-DS is simulated NS-2 traffic, not captured from a real sensor network.
  • CIC-IoT-2023 was subsampled from 46.7 million records to ~199k for feasibility.
  • One attack class (Edge-IIoT Spoofing) has very few samples, so metrics for it are shaky.

10 Glossary — every term in plain English

If a word in this project was unfamiliar, it is defined here.

Networks & attacks
WSN
Wireless Sensor Network — many small battery-powered sensors reporting data over radio (e.g. environmental monitors).
IoT / IIoT
Internet of Things / Industrial IoT — everyday or factory devices (cameras, meters, controllers) connected to a network.
IDS
Intrusion Detection System — software that watches traffic and flags malicious activity. What W-SENTRY is.
SOC
Security Operations Center — the room/console where analysts monitor and respond to threats. The dashboard mimics one.
Jamming
Drowning out the radio channel so legitimate devices can't communicate.
Spoofing
Pretending to be another device or address to intercept or inject traffic (includes MITM and ARP spoofing).
DoS / Flooding
Denial of Service — overwhelming a target with traffic so it can't serve real users.
Intrusion / Probe
Reconnaissance and break-in attempts — port scans, password attacks, injection.
MITM
Man-in-the-Middle — an attacker secretly relaying/altering traffic between two parties.
LEACH
A routing protocol for sensor networks; WSN-DS simulates attacks against it.
MQTT / Modbus
Lightweight messaging protocols common in IoT and industrial systems.
TCP / UDP / ICMP / ARP
Core internet protocols — reliable streams, fast datagrams, ping/control, and address lookup, respectively.
Data & features
Dataset / benchmark
A labeled collection of traffic used to train and test models. We use three: WSN-DS, CIC-IoT-2023, Edge-IIoTset.
Feature
A measurable property of the traffic (packet rate, size, flag counts) fed to the model as a number.
Behavioral feature
A feature describing how traffic behaves (volume, rate, burstiness) rather than a protocol-specific field — so it means the same thing across datasets.
Native feature
A dataset's own original columns, used only for same-dataset tests.
Feature distribution
The typical range and shape of a feature's values; mismatched distributions are the root of the domain gap.
Normalization
Rescaling features to comparable ranges so no single one dominates.
Log normalization
Compressing huge value ranges with a logarithm (while keeping order), so a field measured in billions doesn't swamp the rest.
RobustScaler
A scaler that standardizes features using the median and middle 50%, so outliers don't distort it.
Windowing (T=5)
Grouping five consecutive records into a short sequence so the deep model can see patterns over time.
Train / validation / test split
Dividing data into parts for learning, tuning, and final unbiased scoring (we use 70/10/20).
Stratified sampling
Splitting so each part keeps the same mix of classes as the whole.
Models & training
Random Forest
Many decision trees voting together — a strong, fast classical model.
XGBoost
Trees built one after another, each fixing the previous one's mistakes. Powerful on tabular data.
Deep learning / neural network
Layered models that learn their own features from data rather than being told which to use.
CNN (Conv1D)
Convolutional network — slides small filters over the data to detect local patterns.
BiLSTM
A recurrent network that reads a sequence both forwards and backwards to capture time patterns.
Self-attention
A mechanism that lets the model weigh which moments in a sequence matter most.
Class weighting
Telling the model to care more about rare classes so they aren't ignored.
DANN
Domain-Adversarial Neural Network — trained so its features work across datasets, not just one.
Gradient reversal
The trick inside DANN: it punishes the model for being able to tell which dataset a sample came from, forcing dataset-independent features.
Domain / domain adaptation
A "domain" is one data source (here, one dataset); domain adaptation makes a model work across several.
Transfer learning
Reusing what a model learned on one task/data for another.
Overfitting
Memorizing the training data's quirks so well that performance on new data suffers.
Generalization
The opposite and the goal — performing well on data never seen in training.
Inference / latency
Running a trained model to get a prediction, and how long that takes (must be low for live use).
Metrics
Accuracy
Share of all predictions that are correct. Misleading when one class dominates.
Precision
Of what was flagged as an attack, how much really was (few false alarms = high).
Recall
Of all real attacks, how many were caught (few misses = high).
F1 score
A balanced single score combining precision and recall.
FAR
False Alarm Rate — share of benign traffic wrongly flagged. Lower is better.
Confusion matrix
A grid of true vs. predicted classes; the diagonal is correct, off-diagonal shows which mistakes happen.
Support
How many real samples a class has — small support makes its metrics unreliable.
Transfer accuracy
Accuracy on a different dataset than the one trained on.
Domain gap
The accuracy drop from same-dataset to cross-dataset testing.
Calibration
Whether a model's confidence matches how often it's actually right.
ECE
Expected Calibration Error — how far off that confidence is. Lower is better.
Temperature (T)
A dial that corrects over/under-confidence; T>1 softens an overconfident model.
ROC curve
The trade-off between catching attacks and raising false alarms as sensitivity changes.
AUC
Area under the ROC curve — one number for that trade-off (1.0 perfect, 0.5 random).
Systems & tooling
scapy
A Python library for capturing and crafting network packets (used for the real live capture).
Packet capture / promiscuous mode
Reading traffic off a network card, including traffic not addressed to this machine.
Npcap
A Windows driver that lets software capture packets.
Firewall / netsh / iptables
The system that blocks traffic, and the Windows (netsh) and Linux (iptables) commands to add rules.
Rate limiting
Allowing only a capped amount of traffic from a source instead of fully blocking it.
Mock / simulated feed
Fake-but-realistic data generated in the browser so the dashboard demos without a live network.
React / Vite / Tailwind
The tools the dashboard is built with — a UI library, a fast build tool, and a styling system.
